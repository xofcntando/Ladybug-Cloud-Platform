# New WhatsApp Web features

This document describes three features added to the WhatsApp Web console in Ladybug Cloud: **Chat Digest**, **Notes & Follow-ups**, and **Auto-translate chats**. All three are additive. They do not change the behaviour of existing tools such as anti-delete, broadcast, response radar, labels, or the automation rules, and they do not introduce a new database, a new service, or an AI provider.

The console is served from `public/js/app.js`, which builds the WhatsApp shell and then calls `init(ctx)` on every feature module it finds on `window`. The three new modules follow that same contract, so they are loaded with a `<script>` tag in `public/index.html`, registered in the init loop in `app.js`, and given a rail button next to the existing ones. Each module removes any open dialog before opening its own, which keeps the single-panel rule the rest of the console follows.

## Chat Digest

Chat Digest answers a simple question that the existing console could not: what happened in this conversation over the last week? Open a chat, click the digest icon in the left rail, and the platform reads that chat's message snapshot and produces a factual summary. It shows the message count split into incoming and outgoing, the people involved, the words that come up repeatedly, the media mix, a 24-hour activity chart, and four short lists: questions from the other side that are still waiting for a reply, requests and deadlines, decisions and commitments, and the longest or most substantive messages. Links that were shared are collected separately so they can be opened without scrolling back through the thread. A selector switches the window between 7, 30 and 90 days.

The summariser lives in `lib/wa-digest.js` and has no dependencies. It is deliberately not an AI feature. Messages are already held by the bot process, and the console promises users that message content never leaves their server, so sending a transcript to a third-party model would break that promise and add an API key and a per-message cost. Instead the module tokenises the text, removes a large stop-word list, counts the remaining terms, and applies conservative regular expressions for questions, requests and decisions. A question is treated as answered when any outgoing text message appears after it, which is a heuristic but one that matches how people actually read a thread. Deleted messages still count in the totals but are not attributed to a participant, so a deleted message cannot create a phantom person in the summary.

The endpoint is `GET /api/bots/:id/web/digest?jid=...&days=7`. The handler in `lib/webconsole.js` asks the bot for the newest 200 messages through the existing RPC bridge. If the bot is stopped, or if it does not answer within twelve seconds, the handler reads the same chat from `lib/chat-archive.js` instead and marks the response `offline: true`, which the panel shows as a short note. That means a digest is still available for a number that is offline, which is useful when reviewing a conversation before restarting a bot. The response also reports `sampled` and `truncated`, so the UI can say when it is looking at the latest 200 messages rather than the whole history.

## Notes & Follow-ups

Notes & Follow-ups is a small private CRM attached to each chat. A note is free text up to 2,000 characters, for example "prefers voice notes, call after 6pm". A follow-up is a short reminder with a due date, for example "chase the signed PO on Friday". Both are stored platform-side in `db.data.waBook[botId]`, alongside labels and saved contacts, so they survive a browser change and, when `MONGODB_URI` is configured, a redeploy. They are never sent to WhatsApp and the platform never messages a contact on the user's behalf. The rail button carries a badge with the number of follow-ups that are due, refreshed when the console loads and every two minutes afterwards.

The storage functions are in `lib/wa-book.js`: `notesView`, `saveNote`, `deleteNote`, `addFollowup`, `updateFollowup` and `deleteFollowup`. They validate the chat JID against the same pattern used elsewhere, trim and normalise text, cap a note at 2,000 characters and a follow-up at 300, reject a due date more than a day in the past or more than a year in the future, and refuse to keep more than 200 open follow-ups per bot. Saving an empty note deletes it, which makes the textarea behave the way people expect. Each bot has its own book, so two numbers on the same account never see each other's notes.

The HTTP surface is `GET` and `POST /api/bots/:id/web/notes`, `POST /api/bots/:id/web/notes/delete`, `POST /api/bots/:id/web/followups`, `PUT /api/bots/:id/web/followups/:followupId` and `DELETE /api/bots/:id/web/followups/:followupId`. Every route uses `requireAuth` and `ownBot`, so a user can only read or write notes for a bot they own. The panel has two tabs. Follow-ups are sorted with open items first and then by due date, overdue rows are highlighted, and each row can be marked done, reopened, deleted, or opened as a chat. Notes are sorted by most recently updated. Both tabs have an "Add note" and "New follow-up" action that let the user pick a chat from a dropdown, so a reminder can be created without first opening the conversation.

## Auto-translate chats

Auto-translate reuses the platform's existing `/translate` endpoint, which already caches results for an hour and already runs on the server rather than on the bot's phone. The new module, `public/js/wa-translate.js`, adds a per-bot preference in `localStorage` under `wa_tr_<botId>` holding the target language and a map of chats where automatic translation is switched on. The panel lets the user choose one of twenty languages, toggle automatic translation for the chat they are reading, translate the current chat immediately, and switch automatic translation off for any chat in the list.

When a chat has automatic translation enabled, the module hooks `WAX.afterPaint`, the same hook chain used by the pro module, and decorates incoming text bubbles with a small translation block under the original message. Only the newest 25 bubbles are considered on each paint, translations are cached in memory by message id, and requests are spaced 260 ms apart so a busy thread cannot flood the translation endpoint. If a translation fails, the original message stays untouched and the bubble is marked so it is not retried in a loop. Outgoing messages and non-text messages are skipped. Because the translation happens on the platform, the bot's number never contacts a translation service, which is the same privacy property the existing manual translate button already had.

## Verification

`test/wa-features.test.js` covers the summariser and the notes/follow-up store with 57 assertions. It checks totals, window filtering, millisecond timestamp tolerance, link and request detection, participant attribution, note truncation and deletion, follow-up validation and caps, and bot isolation. It runs with `npm test` and uses a temporary `DATA_DIR`, so it never touches real data.

`test/ui-harness.js` is a Playwright script that logs in against a running server, opens the console for a seeded bot, and checks that the three rail buttons exist, that the digest renders its sections and switches windows, that a follow-up can be created and marked done, that notes appear under their tab, and that the translate panel renders. It runs with `npm run test:ui` and writes screenshots to `outputs/`. Both suites pass against the seeded offline bot, which also exercises the archive fallback path.

## Safety notes

None of the three features sends a message, edits a message, or contacts a third party on the user's behalf. Notes and follow-ups are local metadata. The digest is computed from data the platform already stores. Auto-translate calls the same endpoint as the manual translate button and caches the result. The only new writes are to `db.data.waBook`, which is already the home of labels and saved contacts, and the existing store's debounced save and Mongo sync handle them like any other book change.
